# Research report: improving retrieval, evidence use, and review

**Date:** 2026-10-10  
**Scope:** Research and experiment design only. No implementation, paid model run, or new quality result is claimed in this report.  
**Project:** Streamlit issue investigation and follow-up assistant. The attached course brief is background for the project's objectives; the experiments below are proposals, not instructions taken from that document.

## Executive summary

The highest-value opportunity is **evidence use after retrieval**. In the saved live case `GH9218`, the official upload/memory source and API documentation were in the five-passage context. The draft selected a weaker sentence about deletion instead of the direct `BytesIO`/RAM sentence, mixed observation with causal inference, asked several environment questions, failed one repair, and ended in a fallback. The judge also showed inconsistent aggregate scores and unit findings. See [the case diagnosis](QUALITY_V220_ANSWER_DIAGNOSIS_FA.md) and [the latest experiment result](QUALITY_V221_RESULT_FA.md). The v2.21 live attempt was interrupted before an answer, so it cannot establish an improvement.

The research supports a staged program:

1. Build **span-level, human-reviewed evaluation labels** and calibrate the judge. Source-ID coverage alone misses the failure seen in `GH9218`.
2. Test **small, precise retrieval units with their parent context**, query-aware passage selection, and context ordering before buying new embeddings or models.
3. Compare hybrid/faceted retrieval and reranking with the same frozen corpus and answer model. The current split-query result is mixed, so no automatic promotion is justified.
4. Make generation and review operate on **atomic claims with provenance and applicability**. Measure the actual displayed answer and the fallback, not just retrieval recall or the judge verdict.

These are hypotheses for this corpus, not transferred performance claims. For example, Anthropic reports lower retrieval failure from contextual indexing and reranking on its datasets; that result does not predict this project's gain without a local test. [Anthropic contextual retrieval](https://www.anthropic.com/engineering/contextual-retrieval). Research also shows that adding more retrieved text can increase noise sensitivity, so “more chunks” is not a default remedy. [RAGChecker](https://arxiv.org/abs/2408.08067).

## Findings from research and their fit to this project

### Chunking and indexing

Research comparing chunk sizes finds task-dependent tradeoffs: smaller units can help short fact questions, while larger units can preserve context needed for broader questions. The published result is on different datasets, so the useful local test is a controlled size sweep with **the same source text and evaluation spans**, not adoption of a universal size. [Rethinking Chunk Size](https://arxiv.org/abs/2505.21700). The current block-aware approach already preserves fences and tables, so a simple fixed-character splitter could regress code and traceback integrity. Structure-aware chunking is also supported by domain-specific work on document elements. [Financial Report Chunking](https://arxiv.org/abs/2402.05131).

Contextual retrieval adds a short description of where a chunk sits in its document before indexing. Anthropic tested contextual BM25 and embeddings plus reranking and reported a lower top-20 retrieval failure rate; the extra context must be treated as **search metadata**, not an authoritative quotation. [Anthropic contextual retrieval](https://www.anthropic.com/engineering/contextual-retrieval). A no-model prefix of source title, section, API name, and version is a cheaper first test. Late chunking instead contextualizes embeddings before pooling and depends on a compatible long-context embedding model; it is a later option given the current budget and provider uncertainty. [Late Chunking paper](https://arxiv.org/abs/2409.04701).

The practical “retrieve a small unit, expand to surrounding sentences or a parent section” pattern fits a precise technical claim better than sending every entire chunk. LlamaIndex documents a sentence-window implementation; it is an engineering pattern, not evidence of a gain on this corpus. [LlamaIndex sentence window](https://docs.llamaindex.ai/en/v0.10.34/examples/node_postprocessor/MetadataReplacementDemo/). Hierarchical summarization approaches such as RAPTOR target broader, multi-document synthesis and add indexing cost; the issue-triage cases here are usually narrower, so that is lower priority. [RAPTOR](https://arxiv.org/abs/2401.18059).

### Candidate retrieval and packing

Lexical search is valuable for exact API identifiers, exception names, version numbers, and flags; dense search can recover paraphrases. Hybrid search with RRF is established in both research/practice, but weights and candidate depth should be measured locally. [Azure hybrid search overview](https://learn.microsoft.com/en-us/azure/search/hybrid-search-overview), [Azure RRF scoring](https://learn.microsoft.com/en-us/azure/search/hybrid-search-ranking). The current two-view lexical experiment gained one labeled-source hit across 15 cases but lost a labeled source in another case. Query expansion and fusion can drift off topic when alternate queries are weak. [RAG-Fusion](https://arxiv.org/abs/2402.03367).

Reranking can improve ordering after a broad first stage, but a model reranker is another call and may put similar issue narratives above the official explanation. Cross-encoder reranking is a standard two-stage option, while token-level late interaction such as ColBERTv2 is a heavier indexing alternative. [Weaviate reranking overview](https://docs.weaviate.io/weaviate/concepts/reranking), [ColBERTv2](https://arxiv.org/abs/2112.01488). The `GH9218` saved rerank retained both official sources; its failure cannot be explained as omission alone.

Context position matters. In long-context QA, relevant material in the middle was used less reliably than material near the beginning or end. This makes passage order and pack length testable, but the effect size will depend on this model and these short packets. [Lost in the Middle](https://arxiv.org/abs/2307.03172). A fixed top-five policy may also waste budget on easy cases or omit a necessary second source on hard cases; an adaptive-k method is a candidate for offline comparison. [Adaptive-k study](https://arxiv.org/abs/2506.08479).

### Evidence, citation, and judge design

RAG evaluation should separate whether a passage was retrieved, whether the answer used the relevant content, and whether the answer is supported. [RAGChecker](https://arxiv.org/abs/2408.08067) and [RAGAS](https://arxiv.org/abs/2309.15217) offer complementary metric families; neither automatically supplies a trustworthy project-specific ground truth. Citation benchmarks show that a plausible citation can fail to support the associated statement. [ALCE](https://arxiv.org/abs/2305.14627). `GH9218` is an exact example: an official source appeared in context, but the selected deletion sentence did not directly support all the generated RAM/rerun claims.

Long answer fields can mix supported and unsupported assertions. Atomic fact evaluation and claim-triplet checking are better conceptual fits than treating an entire paragraph as one indivisible claim. [FActScore](https://arxiv.org/abs/2305.14251), [RefChecker](https://arxiv.org/abs/2405.14486). For this assistant, the unit types must distinguish (a) quoted user observation, (b) documented product behavior, (c) uncertain hypothesis, and (d) procedural next step. A procedural request should be checked for usefulness and whether it repeats supplied facts; it does not require a product citation unless it embeds a technical premise.

LLM judges are useful but can exhibit position and verbosity bias, and a single numeric score may conceal contradictory reasoning. [MT-Bench judge study](https://arxiv.org/abs/2306.05685), [position-bias study](https://arxiv.org/abs/2406.07791). Detailed rubrics and reference material can improve consistency, but need local calibration against human labels. [Prometheus](https://arxiv.org/abs/2310.08491). ARES uses a small human-labeled set to correct automated evaluation estimates; its key lesson here is to keep human calibration in the loop. [ARES](https://arxiv.org/abs/2311.09476).

Selective retrieval or corrective action when evidence is poor is also relevant, provided it does not create extra uncontrolled calls. CRAG uses a retrieval-quality gate; Self-RAG studies retrieval only when useful. This project can first try a deterministic evidence-sufficiency gate before considering model-directed retrieval. [CRAG](https://arxiv.org/abs/2401.15884), [Self-RAG](https://arxiv.org/abs/2310.11511).

## Evaluation contract before experiments

**Unit of comparison:** the same frozen case input, source corpus, source versions, query date, model, prompt except for the named factor, and budget policy. Record the source snapshot hash, branch commit, model ID, pricing assumptions, cache status, and output hash for every run. Do not tune on the final held-out set. The 15 existing `dev` source labels can screen variants, but are too small and coarse for a claim of overall improvement.

**Gold annotations to add:** for at least 30 representative cases, two reviewers independently mark the answer-bearing source span(s), source authority, version applicability, important facts already supplied, one useful next action (or acceptable alternatives), forbidden overclaims, and whether a source-free answer is appropriate. Include bugs, feature requests, code/traceback cases, version-sensitive cases, cases with an official answer, and cases with no adequate source. Resolve disagreements without showing variant identity; keep original labels and adjudication. Record inter-annotator agreement and publish only safe excerpts. At least 10 cases should remain untouched until a final comparison; larger held-out coverage is preferable if available.

**Primary metrics:**

- **Retrieval:** answer-bearing span recall@5 and @10, MRR of the first answer-bearing span, context precision, official-source applicability, version mismatch rate, and whether code/fences remain intact. Source-ID recall is secondary.
- **Evidence use:** fraction of required gold facts present in the selected quote set; selected-quote precision; unsupported technical claims per answer; citation entailment at the atomic claim level; source/version attribution errors.
- **User-facing answer:** blind human pairwise preference and rubric scores for factual support, relevance to the ticket, a single discriminating next step, no repeated request, readable language, and concise fallback. Measure the displayed response, not only hidden draft or judge verdict.
- **Review:** false reject/false accept against human claim labels, contradiction between aggregate scores and unit verdicts, repair success, judge contract failures, and stability under equivalent wording and answer-order swaps.
- **Operations:** confirmed plus uncertain reserved spend, provider requests, p50/p95 latency, fallback rate, and transport-error rate. An interrupted or missing run is `unknown`, never a quality success.

Use paired case-level deltas and bootstrap uncertainty intervals for quantitative comparisons; show every regression and raw denominator. With a small test set, use confidence intervals as uncertainty descriptions rather than a binary significance claim. Blind the reviewers to variant names and rotate answer order. Fix the scoring rubric and thresholds **before** opening held-out outcomes. Source-level labels alone can make a method look better while the right sentence is absent.

**Promotion rule for every experiment:** no increase in unsupported product claims or version-invalid claims; no regression on safety and no internal error text exposed; a meaningful improvement in at least one pre-registered primary metric without a material decline in answer usefulness, cost, or latency. “Meaningful” thresholds should be locked from the baseline and annotation noise, rather than chosen after seeing results. A one-case improvement is a diagnosis, not a release decision.

**Cost policy:** all retrieval/chunking/quote/judge-calibration replay experiments start offline. No live run is part of this report. If later authorized, use a fixed small paired subset, one shared ledger that counts uncertain reservations, cached corpus/embeddings where valid, a per-run cap, and an overall cap agreed for that round. Do not multiply live calls across the full matrix. The last incomplete live request reserved $0.007932144 and remains uncertain in the ledger.

## Experiment register

Each experiment changes one factor. `B` means the current branch behavior on the frozen snapshot. For retrieval tests, the answer model stays fixed or is not called. For judge tests, saved drafts and evidence stay fixed. For end-to-end tests, the same cases and spending cap are paired.

| ID / priority | Hypothesis and variants | Primary readout and decision condition | Cost / principal risk |
|---|---|---|---|
| **E0 / prerequisite: span gold** | Annotate exact supporting spans and next-step alternatives rather than only source IDs. Compare current source-label recall with span recall. | Annotation agreement; count cases where a labeled source is present but the answer-bearing span is absent or buried. Lock the evaluation set before tuning. | Human time; reviewer disagreement and dataset leakage. |
| **E1 / high: chunk size and boundary** | `B` section blocks at 1,600-byte target vs 400/800/1,200/2,400-byte targets, same overlap policy; separately compare overlap 0/256/512 bytes. Fences/tables stay atomic. | Span recall@5, answerable context bytes, code integrity, duplicate fraction, and version metadata retention. Do not choose by source recall alone. | Offline. Smaller chunks can omit qualifications; larger chunks add noise. |
| **E2 / high: small-to-parent retrieval** | Rank sentence/paragraph child spans, then present child only, child + adjacent one/two sentences, or parent section with the child highlighted. Keep original source coordinates. | Exact quote recall and human answer support at the same byte budget; inspect whether expansions introduce conflicting version text. | Offline first; more indexing. Child context must not become a forged quote. |
| **E3 / high: contextual index text** | `B` raw text vs deterministic prefix (source title, section, API, version, doc kind) for BM25; later compare a generated 50–100-token contextual description, if budget permits. Only original text is citable. | Span recall@5/10 and distractor rate by source kind; measure index size and prefix-induced false positives. | First variant offline; generated prefixes have indexing cost and may hallucinate. |
| **E4 / high: quote selection** | `B` existing quote candidates vs focused two-candidate selection vs sentence-window selection with explicit qualification capture. Compare exact selected spans using saved contexts. | Quote precision/recall, proportion of claims directly entailed by chosen quote, `GH9218` `BytesIO`/RAM selection, and missing caveats. | Offline replay, then small paired live test. Over-short quotes can lose conditions. |
| **E5 / high: query facets** | Single current query vs title+API/error and symptom views; test RRF weights/candidate depths on `dev` only. Add a fallback to the single query when a facet is empty or drifts. | Span recall@5 and per-case regressions, especially `GH14710`, `GH16388`, `GH17119`; official relevance and bytes. | Offline. Existing split result is mixed; no unconditional enable. |
| **E6 / medium: retriever modality** | BM25 alone, dense alone, BM25+dense RRF, and a rule-based route using exact identifiers/version as signals. Same corpus/chunks; keep embedding model and index hash fixed. | Span recall, MRR, applicability, cost and latency; report performance by exact-identifier vs paraphrase case. | Offline if embeddings are already valid; otherwise indexing cost. Never compare a fixture vector to a paid live vector as equivalent. |
| **E7 / high: reranker objective** | No rerank, saved current model rerank, simple evidence-utility score, and optionally a local cross-encoder on the same top-20. Rubric asks whether a candidate supports a necessary claim, not just topic similarity. | Span MRR, evidence precision, final-answer support on a small paired subset, cost per useful answer; verify official sources are not demoted merely by similar issue reports. | Saved-output replay first. A new model call can offset gains and introduce drift. |
| **E8 / high: pack size/order** | Fixed 5 vs adaptive 2–7 under the same byte cap; test answer-bearing span first, current order, and source-kind grouping. Deduplicate near-identical passages and reserve room only when a directly relevant official source exists. | Human-supported answer rate, claim citation precision, cost, latency, and position sensitivity. | Offline pack replay, then small live pair. Too little context can suppress qualifiers; more can add noise. |
| **E9 / high: version and authority** | Current warning/penalty vs hard separation of exact-version official docs, unknown-version official docs, and anecdotal issue reports. Require a displayed applicability qualifier when a product claim relies on unknown-version evidence. | Version-invalid claim rate and useful-answer rate on version-sensitive cases; avoid rejecting all unknown-version evidence. | Offline plus human review. Strict filtering may leave no usable source. |
| **E10 / highest: claim-first answer contract** | Current long fields vs a compact evidence table: `reported observation`, `documented fact + exact span`, `uncertain inference`, and `one next action`; render prose only from these fields. Compare source-free procedural responses where no product fact is needed. | Atomic supported-claim rate, repeated-question rate, next-step usefulness, response length, `GH9218` RAM/uncertainty handling. | Small live pair after offline schema checks. Rigid format can sound mechanical or omit useful context. |
| **E11 / highest: typed judge** | Current unit review vs atomic-unit review with distinct rubrics: observation fidelity, product-claim entailment and version fit, hypothesis uncertainty, and procedural usefulness/novelty. Keep hard deterministic checks separate. | Human-calibrated false accept/reject, score/verdict contradictions, review stability, and repair success on the same saved drafts. | Offline judge replay where possible; paid judge calls only on a small labeled sample. A more elaborate judge can be slower without being better. |
| **E12 / high: repair and fallback** | Current broad one-shot repair vs finding-targeted repair of only invalid atomic units; compare with direct concise safe fallback when evidence is insufficient. Hide internal codes and raw ticket from user-facing text. | Accepted useful answer, unsupported claims, number of calls, fallback readability, and no unsafe state change. | Paired live subset; repair can increase cost or preserve hidden errors. |
| **E13 / medium: evidence sufficiency gate** | Always draft vs cheap rule-based gate that checks for a directly relevant, applicable span; when weak, ask one case-specific missing detail or escalate without invented product facts. Do not automatically browse the web. | Unsupported-claim reduction vs unnecessary abstention, human usefulness, model-call count. | Offline/low cost. False negatives can withhold a helpful answer. |
| **E14 / medium: task routing** | One generic bug/feature flow vs separate bug-diagnostic, feature-request, and version-comparison rubrics, with the same evidence constraints. | Feature requests incorrectly returned as questions, repeated checks in bugs, and maintainer-ready handoff quality. | Small paired live subset. Route errors can dominate benefit. |
| **E15 / medium: robustness** | Perturb ticket order/wording, place a misleading similar issue near the top, and include a source with an explicit later version or injected instruction. Keep gold facts constant. | Span recall, unsupported claims, version fit, injection resistance, judge verdict stability. | Offline adversarial suite. Synthetic perturbations must remain realistic. |

### Experimental sequencing and ablations

**Wave 0 — measurement:** E0, plus a read-only audit of the saved `GH9218` trace. This is necessary because source-ID labels would have counted that retrieval as successful while the answer failed. Freeze the first human-labeled set and held-out split.

**Wave 1 — zero-cost retrieval:** E1–E5, E7–E9 on saved/frozen data. Run one factor at a time, then test only the most promising combinations. Keep a per-case regression table. E1 should report code/table preservation. E3 must separate search-only generated metadata from citable text. Recheck the already mixed split-query result rather than assuming RRF helps.

**Wave 2 — judge calibration:** E11 on saved accepted/rejected drafts, including deliberately good concise answers and deliberately bad but fluent answers. Blind human labels are the reference. Measure false rejects of source-free procedural questions and false accepts of plausible but unsupported causes. Test whether score and unit verdict agree. Calibrate before using judge acceptance as an optimization target.

**Wave 3 — limited end-to-end:** E4+E10, then E11/E12 as separate ablations on a small paired live subset. Compare actual response text with `B`, retaining the same case, model, source snapshot, and budget ledger. Reviewers judge pairs blind. Do not tune further on the held-out set.

**Wave 4 — final verification:** one frozen configuration against the held-out set with human review, budget and latency report, negative-case analysis, and exact commit/data hashes. Report incomplete provider runs separately. Only then decide whether to turn a variant on by default.

### Concrete `GH9218` acceptance probe

The ideal response should attribute the 3.5 GB upload, RAM spike, and 4 GB container limit to **the reporter**; if it states product behavior, cite the exact official `BytesIO`/RAM span with an explicit unknown-version qualifier; avoid asserting OOM as proven; and ask one discriminating question such as the container's `OOMKilled` status if that check was not already supplied. The displayed answer should not contain `judge_rejected`, a copy of the whole ticket, or internal audit language. This is a **single-case regression probe**, not a general benchmark. [Saved diagnosis](QUALITY_V220_ANSWER_DIAGNOSIS_FA.md).

## Ideas to defer or reject unless the early experiments justify them

- **GraphRAG/RAPTOR across the full issue corpus:** useful for broad synthesis, but this project mostly needs one precise API/document span and one next action. Graph indexing and summaries add cost and another provenance layer. [Microsoft GraphRAG documentation](https://microsoft.github.io/graphrag/), [RAPTOR](https://arxiv.org/abs/2401.18059).
- **HyDE or unconstrained model query generation:** a hypothetical document can improve zero-shot dense retrieval, but may invent API behavior or a nonexistent error. Only consider after exact-identifier retrieval is stable, with generated terms treated as search hints, not facts. [HyDE](https://arxiv.org/abs/2212.10496).
- **Automatic external web search on a weak result:** CRAG evaluates this in broader corpora, but this project has a frozen evaluation snapshot and version/provenance requirements. External search would confound the comparison unless separately frozen and reviewed. [CRAG](https://arxiv.org/abs/2401.15884).
- **Blindly raising top-k or making the judge permissive:** larger contexts can bury the best span and introduce relevant-looking noise; the current draft also had genuine unsupported claims. [Lost in the Middle](https://arxiv.org/abs/2307.03172), [RAGChecker](https://arxiv.org/abs/2408.08067).
- **Changing the generation model before stage diagnosis:** a stronger model might help, but would obscure whether the failure is passage selection, answer contract, or review. Keep model comparison as a later, costed experiment with the same frozen inputs.

The linked papers and vendor documentation are evidence about methods **on their own tasks**. No reported percentage from them is represented as a measured improvement here. The most directly applicable sources for the first wave are [RAGChecker](https://arxiv.org/abs/2408.08067) for stage-level diagnosis, [RAGAS](https://arxiv.org/abs/2309.15217) for separate context and answer metrics, [FActScore](https://arxiv.org/abs/2305.14251)/[RefChecker](https://arxiv.org/abs/2405.14486) for atomic claims, [Anthropic contextual retrieval](https://www.anthropic.com/engineering/contextual-retrieval) for contextual indexing, [Lost in the Middle](https://arxiv.org/abs/2307.03172) for pack order, and [ARES](https://arxiv.org/abs/2311.09476) for human calibration.
